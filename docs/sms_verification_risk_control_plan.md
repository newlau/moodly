# 短信验证码风控方案

状态：current plan  
Owner topic：认证 / 短信验证码  
代码 owner：`/Users/liuyingying/Desktop/moodly_server/docs/auth.md`、`/Users/liuyingying/Desktop/moodly_server/src/modules/auth`  
更新日期：2026-06-15

## 1. 背景

短信验证码需要继续保留，用于手机号登录、注册和绑定手机号。

但短信验证码本身有直接成本，也容易被接码平台、脚本、代理 IP、旧版本客户端绕过。因此后续短信能力不再作为低门槛入口，而是作为受人机验证、版本、IP、手机号、provider 预算共同约束的高风险能力。

## 2. 产品结论

最终策略：

- 新版本保留短信验证码。
- 未登录的手机号登录/注册发送验证码前，必须完成 Turnstile 人机验证；已登录用户绑定手机号不需要人机验证。
- 老版本不支持 Turnstile，因此不再允许发送短信验证码。
- 老版本点击获取验证码时，提示用户更新到新版本。
- 华信短信通道停止使用。
- 固定验证码保留，但只作为受控兜底能力，不作为普通用户公开验证码。
- 服务端继续保留手机号、IP、设备、全局预算等多维风控。

一句话口径：

> 手机号登录/注册发送验证码必须做人机验证；已登录的绑定手机号免人机验证但仍受登录态、IP、设备、手机号和预算限流保护；老版本不再支持未登录短信验证，提示升级。

- 短信 Turnstile 最低支持版本：Android `1.0.7`，iOS `1.0.7`；未识别平台时按通用门槛 `1.1.2`。

## 4. 客户端版本策略

| 客户端类型 | 是否允许发送短信 | 产品处理 |
| --- | --- | --- |
| 新版本，支持 Turnstile，Android / iOS 大于等于 1.0.7 | 允许 | 登录/注册先做人机验证，再发短信 |
| 已登录用户绑定手机号 | 允许 | 不做人机验证，仍校验登录态并执行 IP、设备、手机号和预算限流 |
| 未登录的老版本，低于平台最低支持版本 | 不允许 | 提示更新到新版本 |
| 未带版本 / 未知客户端 | 不允许 | 按老版本处理，提示更新 |
| 脚本直接请求接口 | 不允许 | 无有效 Turnstile token，服务端拒绝 |

老版本提示文案建议：

> 当前版本暂不支持短信验证，请更新到最新版后继续使用。

服务端错误码建议：

```json
{
  "code": "UPGRADE_REQUIRED",
  "message": "当前版本暂不支持短信验证，请更新到最新版后继续使用"
}
```

## 5. 新版本发送流程

1. 用户在手机号登录/注册页点击“获取验证码”。
2. 客户端先拉起 Turnstile 人机验证。
3. Turnstile 验证通过后，客户端拿到 `turnstile_token`。
4. 客户端调用 `/v1/auth/send-code`，带上手机号和 `turnstile_token`。
5. 服务端校验客户端版本是否支持 Turnstile。
6. 服务端调用 Cloudflare 校验 `turnstile_token`。
7. 服务端检查手机号、IP、设备、全局预算是否超限。
8. 全部通过后，服务端调用短信 provider 发送验证码。
9. 短信发送成功后，验证码写入 Redis，5 分钟有效。
10. 用户登录或绑定成功后，验证码失效。

已登录用户的绑定手机号流程使用 `/v1/auth/bind/phone/send-code`。该接口必须携带有效登录态，不校验 Turnstile token，但不会放宽短信 provider、IP、设备、手机号或全局预算限制。

## 6. 老版本处理

未登录的老版本不支持 Turnstile，不再允许继续发送短信验证码。已登录用户的绑定手机号不依赖 Turnstile，因此不受此版本门槛影响。

原因：

- 如果给未登录老版本保留无 Turnstile 的短信入口，会绕过新版本强风控。
- 接码平台可以继续通过老版本或伪造老版本请求刷短信。
- 短信成本会继续落到 provider 账单里，难以控制。

产品表现：

- 未登录老版本点击手机号登录或获取验证码时，提示升级。
- 不提供“继续发送验证码”的兜底按钮。
- 如果用户必须用手机号登录，需要先升级新版本。

## 7. 固定验证码策略

固定验证码保留，但定位为内部、审核、紧急兜底能力。

建议规则：

- 只对白名单手机号生效。
- 不对普通用户全量开放。
- 通过服务端配置开关控制。
- 使用固定验证码也要记录审计日志。
- 固定验证码不触发短信发送，不产生成本，但会影响账号安全，因此必须受控。

产品口径：

- 固定验证码不是普通用户能力。
- 固定验证码不替代 Turnstile。
- 普通用户仍然按新版本短信验证码流程走。

## 8. IP 和频率风控

服务端保留并继续收紧多维限流。

建议规则：

| 维度 | 建议限制 |
| --- | --- |
| 同手机号 | 60 秒内最多 1 次 |
| 同手机号 | 每天最多 3 次 |
| 同公网 IP | 每小时最多 3 次 |
| 同公网 IP | 每天最多 10 次 |
| 同设备 | 每天最多 3 到 5 次 |
| 无法识别真实 IP | 按高风险处理 |
| 单 IP 多手机号异常 | 降级或封禁 |
| 单 IP 段异常 | 可临时整体封禁 |

命中限流时返回：

```json
{
  "code": "RATE_LIMITED",
  "message": "请求太频繁，请稍后再试"
}
```

补充说明：

- 风控应使用真实客户端公网 IP。
- 私网 IP 不作为正常风控依据。
- 如果代理层拿不到真实 IP，相关请求按高风险处理。

## 9. 短信通道策略

| 通道 | 策略 |
| --- | --- |
| 火山 | 主短信通道 |
| 华信 | 停止使用，关闭模板、签名、账号调用权限 |
| 阿里云 | 核对账单和旧模板，确认是否仍有短信发送 |
| IPYY | 旧回退通道，不建议继续作为自动兜底 |

通道原则：

- 不建议自动切换备用通道。
- 如果一个通道被刷爆，不应自动切到另一个通道继续消耗。
- 每个 provider 都要设置日预算、月预算、小时突增告警。
- 华信确认停用后，需要从控制台关闭可发送能力，避免旧服务继续调用。

## 10. 监控和数据口径

产品和运营后续看短信成本时，不只看 provider 账单总额，还要看转化和异常。

建议指标：

- 每日短信发送量。
- 每日发送成功量。
- 每日发送失败量。
- 每日成功登录 / 绑定量。
- 短信到登录转化率。
- 单手机号重复发送次数。
- 单 IP 请求手机号数量。
- 各 provider 日消耗、月消耗。
- 老版本拦截次数。
- Turnstile 验证失败次数。
- 限流拦截次数。

异常判断示例：

- 短信发送量上涨，但登录成功量没有同步上涨。
- 单 IP 请求大量不同手机号。
- 某 provider 费用异常上涨。
- 夜间短信量异常高。
- 同一手机号短时间重复请求。

## 12. 产品影响

对新版本用户：

- 仍可使用短信验证码。
- 每次发送前需要完成一次安全验证。

对老版本用户：

- 不再支持短信验证码。
- 需要更新到新版本后继续使用手机号登录或绑定。

对成本：

- 短信消耗会显著收敛。
- 脚本和接码平台直接刷接口的成本风险会降低。
- Provider 账单可以通过预算和流水进一步核对。

对安全：

- 无 Turnstile token 的请求不再发短信。
- 固定验证码受控后，不再作为全局绕过入口。
- 通过 IP、手机号、设备、预算多维限制降低盗刷风险。
