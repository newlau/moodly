## 1. 总体策略

先搭骨架，再接真实能力：

1. 先定接口契约和 mock provider，让双端不用等火山云。
2. 再做双端页面空壳和路由。
3. 再做聊天语音最小闭环。
4. 最后接火山云、扣费、角色码和站内消息。

每一批都必须做到：

- 有明确开关，未完成能力不影响现有聊天。
- 存量角色不展示语音入口。
- API 字段双端一致。
- 有最小可回归测试。
- 有截图或手动验收记录。

当前聊天语音最小闭环采用的链路：

1. 客户端长按录音，生成本地 `m4a/aac` 文件。
2. 客户端调用 `POST /chat/v1/upload/audio` multipart 上传音频，服务端返回稳定 `media_url`。
3. 客户端调用 `POST /chat/v1/chats/:chatId/messages`，传 `content_type=voice`、`media_url`、`duration`、`mime_type`。
4. chat runtime 收到 voice 消息后，如果客户端没传 `asr_text`，先用 ASR 把音频转文字；`VOICE_ASR_PROVIDER=volc` 时走火山极速识别，`VOICE_ASR_PROVIDER=aliyun` 时走阿里云 DashScope/Qwen ASR。mock ASR fallback 仅用于联调/本地兜底，需显式开启 `VOLC_ASR_MOCK_FALLBACK_ENABLED=true`，生产默认不应把 provider 错误伪造成固定文字。
5. 服务端把转写文字作为 `content` 进入模型上下文，同时保留 `media_url/duration/mime_type/asr_text` 给展示层。
6. 如果会话 `voice_id` 已设置且 `voice_frequency != never`，用户语音触发的第一条 AI 文本回复会转为 `content_type=voice`，火山 TTS V3 生成音频并上传，返回 `media_url/mime_type/content/asr_text`。
7. 客户端消息列表和聊天气泡按 `content_type=voice` 渲染：可播放 `media_url`，可展开查看 `asr_text/content`。

Pipecat 实时语音 P0 mock 采用旁路链路：

```text
客户端请求 mock session
-> chat-svr 校验用户拥有 chat
-> 返回 Pipecat local dev runner client_url
-> 客户端连接 Pipecat sidecar
-> sidecar 通过 SmallWebRTCTransport 输出 mock 状态/合成音频
```

该链路当前不写 `messages`，也不进入 `executeReactiveTurn`。后续如果要让实时 transcript 影响角色长期记忆和聊天历史，需要新增 transcript bridge，把最终用户文本作为受控入口回灌现有 reactive ingress。

语音通话商业化 P0 采用独立资产：

```text
通话时长卡购买
-> moodly_server 创建 voice_call order 并核销支付
-> 写 voice_call_credit_ledger，单位 seconds
-> chat-svr 创建 voice_call session
-> 通话结束按服务端有效时长扣 seconds
-> seconds 不足时按 100 糖果/分钟折算补扣糖果
-> 钱包明细记录 session、chat、character、duration、payment_source
```

该资产不得复用 `voice_card_1` 或 `voice_card_ledger`；音色卡继续只用于保存/修改复刻音色。

### 1.1 第 3.5 批测试链路配置与验收

服务端环境变量：

- ASR provider：`VOICE_ASR_PROVIDER=volc` 或 `VOICE_ASR_PROVIDER=aliyun`
- 火山 ASR 新版控制台：`VOLC_ASR_API_KEY`
- 火山 ASR 旧版控制台：`VOLC_ASR_APP_ID` + `VOLC_ASR_ACCESS_TOKEN`
- 阿里云 ASR：`DASHSCOPE_ASR_API_KEY` 或复用 `DASHSCOPE_API_KEY`，默认 `DASHSCOPE_ASR_MODEL=qwen3-asr-flash`
- TTS 新版控制台：`VOLC_TTS_API_KEY`
- TTS 旧版控制台：`VOLC_TTS_APP_ID` + `VOLC_TTS_ACCESS_TOKEN`
- 普通音色资源：`VOLC_TTS_RESOURCE_ID=volc.service_type.10029` 或对应开通资源
- 复刻音色资源：`VOLC_TTS_CLONE_RESOURCE_ID=seed-icl-2.0`
- 输出格式：`VOLC_TTS_AUDIO_FORMAT=mp3`、`VOLC_TTS_SAMPLE_RATE=24000`

测试步骤：

1. 在火山控制台准备一个可用音色 ID。普通音色直接用音色列表 ID；复刻音色测试阶段可先在控制台生成/拿到 `S_...` speaker id。
2. 调 `PUT /chat/v1/chats/:chatId/settings` 设置：
   ```json
   { "voice_id": "S_xxx_or_voice_id", "voice_frequency": "sometimes" }
   ```
3. 客户端或 Postman 上传录音：`POST /chat/v1/upload/audio`，拿 `media_url`。
4. 发送语音消息：`POST /chat/v1/chats/:chatId/messages`，body 至少包含 `content_type=voice`、`media_url`、`duration`、`mime_type`。
5. 预期 user message：`content_type=voice`，`content/asr_text` 是 ASR 后文字，`media_url` 仍是原始录音地址。
6. 预期 assistant message：第一条回复为 `content_type=voice`，有 `media_url`、`mime_type=audio/mpeg`、可展开文字 `content/asr_text`。
7. 如果只配置 ASR 没配置 TTS，AI 不会自动转语音，仍回文本，避免客户端出现无音频语音泡。

当前限制：

- `voice_id` 已支持业务 voice asset id 到 `providerSpeakerId` 的服务端解析；旧的 `S_.../BV...` 直传 provider id 仍兼容。
- 复刻训练 API wrapper 已接入，但真实火山字段、状态码和 demo 音频返回还没做样本 smoke；本地/未配置时走 mock clone fallback。
- 复刻每日重做次数默认仍强校验；当前语音联调如需连续反复生成，部署环境要显式配置 `VOICE_CLONE_DAILY_LIMIT_ENFORCED=false`，否则会返回 `daily clone attempt limit exceeded`。
- 角色创建/编辑接口已支持可选 `voice_id`、`voice_frequency`；`voice_id` 仍是业务 voice asset id，服务端保存到该用户与角色对应 chat 的 `character_chat_settings`，TTS 时再解析到 provider speaker。
- `moodly-chat-svr` 当前 `/chat/v1/voices` 已升级为正式字段兼容数组；`moodly_server` voice 骨架仍在，但当前聊天 runtime 主链路已优先在 `moodly-chat-svr` 收口。
- 视频复刻依赖部署环境安装 `ffmpeg`；客户端会先尝试本地抽 `.m4a`，失败才上传视频由服务端抽音频。音频复刻上传当前直接复用原音频作为 `extracted_audio_*`，后续如 provider 要求更严再由服务端统一标准化为 24k mono 音频。
